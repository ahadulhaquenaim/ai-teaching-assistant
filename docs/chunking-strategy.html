Chunking Strategy

After the file is saved in MongoDB: text → chunks → vectors → Pinecone

The flow

┌─ 0. FILE SAVED (MongoDB)
│      record exists, status = "processing"
│      raw bytes passed to the background task (not stored in Mongo)
│
├─ 1. EXTRACT TEXT per page (PyMuPDF)
│      your PDF: 2 pages → 2 text blocks, tagged page 1 and page 2
│      clean: rejoin hyphenated words, remove extra spaces/blank lines
│
├─ 2. SPLIT EACH PAGE SEPARATELY (RecursiveCharacterTextSplitter)
│      a chunk never mixes two pages → exact page citations
│      for one page:
│        - try to cut at paragraph breaks  "\n\n"
│        - still > 1000 chars? cut at       "\n" → ". " → " " → any char
│        - merge small pieces up to ~1000 chars
│        - next chunk starts with last ~150 chars of previous (overlap)
│
├─ 3. BUILD CHUNK RECORDS
│      (chunk_index, page_number, text)
│      chunk_index counts 0, 1, 2 … across the whole document
│
├─ 4. EMBED (gemini-embedding-001, RETRIEVAL_DOCUMENT)
│      each chunk text → 768-number vector
│      batches of 50, 1 s pause between batches, retry on errors
│      dimension checked (must match Pinecone index)
│
├─ 5. UPSERT (Pinecone)
│      namespace = document_id
│      one record per chunk: id, vector, metadata
│
└─ 6. MARK READY (MongoDB)
       save page_count, chunk_count (+ summary)
       if anything failed before → delete partial vectors, mark "failed"

One page split (about 2000 chars)

page text:  |================== 2000 chars ==================|

chunk 0:    |======== 1000 ========|
chunk 1:                      |150|======= 850 =======|
chunk 2:                                          |150|== rest ==|

|150| = overlap copied from the end of the previous chunk

Your case: 2 pages, ~4000 chars

Page~CharsChunksGlobal chunk_index
12000~30, 1, 2
22000~33, 4, 5

Rule of thumb: chunks per page ≈ page chars ÷ ~850, rounded up. Numbers above are illustrative. Real count depends on paragraph breaks. Your real CV gave 8 chunks, so its pages hold more than 2000 chars each.

What one Pinecone record looks like

FieldValue
iddocument_id + chunk_index
values768-dim vector
metadatadocument_id, page_number, chunk_index, text

Original text is stored in metadata, so chat needs no second lookup. Page number gives the citation.

Who does each job

JobDone by
Read PDF textPyMuPDF
Split into chunksLangChain RecursiveCharacterTextSplitter (rule-based, no AI model)
Chunk → vectorgemini-embedding-001 (768 dims)
Store vectorsPinecone (cosine similarity)
Summary (not chunking)LLM gemini-3.6-flash

The core idea: each page is cut into ~1000-char overlapping pieces at natural breaks, each piece keeps its page number, Gemini turns each piece into a vector, and Pinecone stores vector + text so chat can find and cite it later.

Code: backend/app/services/ingestion.py (chunk_pages), embeddings.py, vectorstore.py. Settings: backend/app/config.py.
